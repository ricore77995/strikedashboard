PERSONA: Engenheiro Pragmático

WEAKNESS-1 [FATAL]: `operationalNotes.ledgerSeparation` ("Every action credits BOTH ledgers") on Vercel + SQLite — A spec inteira assume um dual-ledger write-heavy system. O CLAUDE.md diz literalmente: "Vercel + SQLite: filesystem read-only em serverless. MVP não precisa de escrita." Mas a v3 *exige* escrita em CADA evento: check-in, story, repost, referral, boost activation, streak shield consumption, monthly reset, mini_random assignment, league snapshot. O roadmap só migra para Turso na Sprint 1+. Shipping este spec contra SQLite num serverless é fisicamente impossível — não é "rework", é build error no primeiro POST. E mesmo com Turso, não há definição de transação para a operação atómica "credita pontos + credita XP + reavalia tier + emite mensagem" — vais ter ledgers divergentes na primeira falha de rede entre os dois writes.

WEAKNESS-2 [FATAL]: `boosts.stackingFormula` + `tierEvaluation: "Continuous — tier re-evaluated on every XP credit"` — Race condition garantida. Cenário: aluno faz 3 check-ins quase simultâneos (Yogo polling devolve 3 events num batch). Cada credit dispara: (1) leitura do estado de boosts activos, (2) cálculo do multiplicador com `min(1.0 + sum(delta), 3.0)`, (3) write de points, (4) write de XP, (5) re-avaliação de tier, (6) potencial trigger `streak_5` que activa NOVO boost mid-batch. Sem lock pessimista por `customer_id` (SQLite/Turso não tem `SELECT FOR UPDATE` decente, Turso é libSQL distribuído), o segundo check-in lê estado stale e aplica o boost antigo OU o novo — não-determinístico. O `boostStackingExample` no spec calcula "0.8 + 1.0 + 0.4 + 0.6 = 2.8" como se fosse pure function; na realidade vais ter duas writes paralelos a chegar a totais diferentes para o MESMO evento.

WEAKNESS-3 [FATAL]: `triggers.streak.streak_5/10/15` sem webhooks Yogo + `integrations.yogo.connection: "WhatsApp bot pulls data on demand"` — Streak detection depende de polling. Vercel Hobby tem cron daily-only. Se polas Yogo 1x/dia às 02:00, o streak_10 só dispara ~26h depois do check-in real. Pior: `streak_shield` "1 missed day AND shield_available_this_month" requer detectar o dia *exacto* em que falhou; polling diário pode confundir "faltou ontem mas treinou hoje" com "treinou ontem mas o polling de hoje ainda não correu". E o `multi_class_same_day` ("classesToday >= 2") falha completamente — se polas à meia-noite, nunca vês duas aulas hoje, só duas aulas *ontem*. Spec assume realtime check-in events que o Yogo não expõe.

WEAKNESS-4 [FATAL]: Identity resolution não está definida em lado nenhum — Os triggers misturam `manychat_story_mention`, `subscription_renewed` (Yogo), `2_students_checkin_same_class AND both_report_via_bot` (WhatsApp), `referred_user_signs_up` (?). Não há schema para mapear: IG handle ↔ ManyChat `subscriber_id` ↔ WhatsApp `phone_e164` ↔ Yogo `customer_id` ↔ StrikeLab `student_id`. CLAUDE.md flagga explicitamente "ManyChat Pro Instagram @ mention detection has known false negatives" — agora multiplica isso por uma cadeia de 4 IDs sem chave única. O `embaixador_ratio` ("stories_count_this_month > checkins_count_this_month") é o pior caso: cruza dois sistemas com identidades diferentes em tempo real. Vais creditar pontos à pessoa errada ou perder eventos silenciosamente.

WEAKNESS-5 [MAJOR]: `operationalNotes.monthlyReset: "Day 1 at 00:00 Europe/Lisbon"` + Vercel Hobby cron daily-granularity — A cron daily corre numa janela UTC fixa, não às 00:00 Lisboa. DST shift (Mar/Out) parte o reset em ~1 hora. Mais grave: spec não define idempotência. Se a cron timeout (Vercel função 10s no Hobby, 60s Pro), faz reset parcial — alguns users já têm `monthlyPoints=0`, outros ainda têm 8500. Não há audit trail definido, não há "reset_attempt_id", não há lock para impedir double-run. Eventos que chegam durante o reset (story às 23:59:30 do dia 30, processado às 00:00:05 do dia 1) — credita ao mês antigo ou novo? Spec silencia.

WEAKNESS-6 [MAJOR]: `boosts.mini_random` "2-4x per week, randomly assigned" — Spec não diz QUEM assigna, QUANDO assigna, a QUEM assigna. É por aluno? Global? Cron? Triggered no check-in? "Duration: single class" — qual classe? A próxima? A actual? Se o aluno tem mini_random "pendente" e faz 3 aulas na quarta, qual consome o boost? Sem state machine definida, isto é impossível de implementar de forma reproduzível. Adicionalmente, "randomly assigned" significa que precisas de um RNG seedado por aluno+semana, senão dois deploys diferentes dão resultados diferentes — ou pior, replays do event log dão pontos diferentes.

WEAKNESS-7 [MAJOR]: `antiAbuse.storyCheckInDetection: "Bot queries Yogo for check-in in last 24h"` — Esta query assume que o Yogo `/classes` endpoint expõe check-ins por customer numa janela temporal. O CLAUDE.md descreve o endpoint como `GET /classes?startDate=...&populate[]=...` — orientado a *classes*, não a check-ins por aluno. Não há evidência no projecto de que isto devolve "este customer fez check-in nas últimas 24h" sem fazer N+1 queries iterando classes. A diferença entre `story_checkin` (80 pts) e `story_organic` (250 pts) — 3x diferença — depende inteiramente desta query funcionar correctamente. Falsos negativos = pagas 250pt em vez de 80pt = inflação.

WEAKNESS-8 [MAJOR]: `referral_converted.phase_2_first_renewal` + `minRenewalsByReferred: 1` — Yogo não tem webhook de "subscription_renewed". O `renewal_processed` trigger (+400pt + boost) também depende disto. Detecção via polling do `/reports/memberships-list` requer diff contra snapshot anterior. Se o polling falha 2 dias, perdes renewals. Se a renovação é manual (Marcelo lança no Yogo a 5 do mês), o boost de 14 dias começa quando? Quando o aluno renovou conceptualmente, quando o Marcelo lançou, ou quando o polling detectou? Os três timestamps são diferentes e o spec não escolhe um.

WEAKNESS-9 [MAJOR]: `monthlyPrizes.leagueOfChampionsRule` "Top 3 of category in month N → out of main ranking in month N+1" — Requer snapshot histórico de pontos por categoria por mês. Não há schema definido. Pior: eventos *atrasados* (story do dia 30 detectado pelo ManyChat dia 2) — entram em N ou N+1? Se entram em N, o "Top 3" muda retroactivamente depois do prize ser anunciado. Se entram em N+1, o aluno excluído da ranking principal recebe pontos que ninguém vê. E o `winnerBroadcast` (publicado no WhatsApp grupo) torna isto irreversível socialmente.

WEAKNESS-10 [MAJOR]: Event log append-only growth sem aggregation strategy — Cada check-in dispara potencialmente 5+ writes (points, xp, boost state, streak counter, tier eval). Para ~200 alunos activos a 8-20 aulas/mês = ~2000-4000 check-in events/mês, multiplicado por triggers UGC, referrals, challenges. Turso Hobby tem 9GB storage e 1B row reads/mês — atinges os reads em poucos meses com `tierEvaluation: "Continuous — tier re-evaluated on every XP credit"` se cada eval lê o ledger completo. Spec não define agregação mensal, snapshots, ou retenção.

WEAKNESS-11 [MINOR]: `streak_shield` "1x per month, auto-applied" + `broken_streak.condition: "shield_already_used_this_month"` — Race condition: aluno parte streak no dia 31, shield consume-se. No dia 1 (reset), o shield reset também? Spec diz "boosts mensais reset" mas shield não é boost, é "action". Aluno parte streak novamente no dia 2 — `shield_already_used_this_month` é false (mês novo) mas o streak counter ainda está visível do mês anterior? Ambiguity.

WEAKNESS-12 [MINOR]: `boosts.weekend` "48h cyclical (always active on weekends)" vs `streak_10.duration_days: 14` — Como queryas "boosts activos AGORA" eficientemente? Weekend é regra de calendário, os outros são rows com TTL. Sem schema híbrido definido (computed boosts vs stored boosts), cada check-in faz scan a múltiplas tabelas. E o `embaixador_ratio` é *computed em tempo real* contando duas counters — outro scan por evento.

VERDICT: O spec é uma especificação de produto travestida de spec técnica — assume um event-driven realtime backend com transactions ACID que o stack actual (Vercel serverless + SQLite/Turso + polling Yogo + ManyChat sem identidade unificada) literalmente não consegue fornecer, e qualquer tentativa de shipping vai produzir ledgers corrompidos no primeiro fim-de-semana com tráfego real.
